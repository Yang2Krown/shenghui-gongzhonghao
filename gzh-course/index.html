三层过滤：省钱的艺术

嵌入（Embedding）是需要花钱的 API 调用。为了省钱，系统在嵌入之前设置了三层过滤：

1
时间过滤

超过 90 天的内容直接丢弃。过时的资讯没有价值。

2
AI 相关性过滤

用关键词判断内容是否和 AI 相关。不相关的直接跳过。

3
权重过滤

低权重来源（weight ≤ 2）的内容直接跳过。因为这些来源质量不高，不值得花钱做嵌入。

💡
这个设计很聪明

只有通过三层过滤的内容才会被送去嵌入。这就像一个漏斗——先用免费的规则筛掉大部分垃圾，再用花钱的 AI 处理精华内容。成本可能降低 60-70%。

语义聚类：让计算机"理解"文字

计算机不懂中文。但如果我们把一段文字变成一组数字（向量），计算机就能计算两段文字的"距离"——距离越近，意思越相似。

Python # 嵌入：把文字变成 1024 维的数字数组 embedding = await embed("GPT-5 发布了新功能") # 结果：[0.023, -0.156, 0.891, ...]（共 1024 个数字） # 语义聚类：和已有信息比对 for existing in existing_embeddings: distance = cosine_similarity(embedding, existing) if distance > 0.85: # 非常相似，归为同一组 merge_into_cluster(existing, new_info)
English
第 1-3 行：调用 DashScope 的嵌入 API，把"GPT-5 发布了新功能"变成 1024 个数字
第 5-9 行：遍历所有已有的信息向量，计算新信息和每个已有信息的"距离"
第 7-8 行：如果距离 > 0.85（非常相似），就把它们归为同一组（InfoCluster）
类比：就像图书馆把同一主题的书放在一起——系统把讨论同一话题的文章归为一组
📊
pgvector：向量数据库

这些向量存储在 pgvector 中。它能在百万级向量中快速找到最相似的几个——这比遍历所有向量快得多。阈值 0.85 意味着只有"非常相似"的内容才会被合并。

波次调度：避免把 API 打爆

系统每天要从 13 个信息源抓取数据。如果同时请求所有源，很容易被 API 限流甚至封禁。

🌊
波次调度（Wave Scheduling）

想象你在餐厅点菜。如果 100 个人同时点菜，厨房会崩溃。但如果分 5 波，每波 20 个人，每波之间等 2 分钟，厨房就能从容应对。系统的爬虫也是这样——每天 5 波（06:00、10:00、14:00、18:00、22:00），每波内的源按 90 秒间隔依次请求。

Python # 限流并发抓取（最多 5 个同时跑，避免 API 限流） sem = asyncio.Semaphore(5) task_sources = [] tasks = [] for src in sources: adapter = self.get_adapter(src.source_type) async def _limited_fetch(a=adapter, s=src): async with sem: return await self._fetch_one(a, s) tasks.append(_limited_fetch())
English
第 2 行：创建一个"信号量"（Semaphore），最多允许 5 个爬虫同时运行
第 4-5 行：遍历所有需要抓取的信息源
第 7-9 行：每个爬虫在执行前必须先获取"通行证"（async with sem）
类比：就像高速公路的收费站——最多 5 个车道同时通行，其他的排队等候

双重去重：同一条信息不会出现两次

不同信息源可能报道同一件事。系统用两种方式防止重复：

💾

内存去重

同一波次内，用内存中的 Set 记录已经处理过的标题哈希。新加入的记录在数据库中还不可见，所以需要内存去重。

🗄️

数据库去重

跨波次去重，查数据库中是否已有相同标题（哈希匹配）或完全相同的 URL。这是最终防线。

⚠️
为什么需要双重去重？

如果只用数据库去重，同一波次内新增的记录在数据库中还查不到（因为还没 commit），就会导致重复。内存去重解决了这个问题。

微信公众号 API：最后一公里

文章写好后，需要推送到你的微信公众号草稿箱。系统直接调用微信的官方 API，不需要你手动复制粘贴。

Python async def get_access_token(appid: str, secret: str) -> str: """获取微信公众号 access_token""" url = to_ipv4_url(f"{WECHAT_API_BASE}/token") params = { "grant_type": "client_credential", "appid": appid, "secret": secret, } async with wechat_client(timeout=15) as client: resp = await client.get(url, params=params) resp.raise_for_status() data = resp.json() if "access_token" not in data: raise ValueError(f"获取失败: {data}") return data["access_token"]
English
第 1 行：定义一个异步函数，输入 appid 和 secret（微信公众号的账号密码），输出 access_token（临时通行证）
第 3 行：to_ipv4_url() —— 强制使用 IPv4。为什么？因为微信 API 的 DNS 有时会解析到 IPv6，而服务器可能不支持 IPv6
第 4-8 行：构造请求参数——grant_type 表示"我要用账号密码换 token"
第 9-11 行：发送 GET 请求，15 秒超时
第 13-16 行：检查返回结果——如果没有 access_token，说明失败了，抛出错误
⚠️
微信 API 的两个坑

坑 1：微信 API 的 DNS 有时会解析到 IPv6 地址，但服务器可能不支持 IPv6。所以代码强制用 to_ipv4_url() 转换成 IPv4 地址。

坑 2：微信 API 默认会把中文转义成 Unicode 编码（如 你好），导致解析失败。所以代码用 ensure_ascii=False 保持中文原文。

Redis + Celery：后台任务队列

爬虫和 AI 流水线都很耗时——可能需要几分钟甚至更久。如果让用户一直等着，体验会很差。

📮
邮局比喻

想象你去邮局寄包裹。你把包裹交给柜台（提交任务），然后就可以走了（不用等）。邮局会安排分拣员（Celery Worker）处理你的包裹。你随时可以来查进度（轮询 Progress API）。Redis 就是那个"待处理包裹架"——所有任务先放在这里，分拣员按顺序取走处理。

⚡

Redis

内存数据库，速度极快。在这里充当"消息队列"——存放待处理的任务。也用于缓存和会话管理。

🔄

Celery

分布式任务队列。接收任务 → 放入 Redis → Worker 取出执行。支持定时任务（Beat）、重试、超时等。

📊

Progress API

前端通过轮询 /progress 接口获取任务进度。每个 Agent 完成后更新进度，前端实时显示"正在执行 Agent A..."

聪明的工程技巧

这个系统里有几个特别聪明的设计——理解它们，你就能在自己的项目中复制这些模式

"创造者而非过滤器"哲学

传统的信息处理思路是：爬 100 条 → 过滤到 10 条 → 输出。但这个系统反其道而行之：

🎯
核心洞察

Agent A（选题衍生员）不是从一堆烂选题里挑好的——它是主动创造好选题。给它 1 条资讯，它能衍生出 3-8 个高质量的候选选题。这就像一个创意总监，不是在废纸篓里找创意，而是从零开始构思。

❌

传统思路：过滤器

爬 100 条 → 用规则过滤掉 90 条 → 剩下 10 条 → 输出。问题是：如果原始数据质量不高，你过滤后也没好东西。

✅

这个系统：创造者

爬 1 条 → Agent A 衍生 5 个好选题 → Agent B 独立评分 → 输出最好的。原始数据质量低也没关系，Agent A 会创造价值。

程序化分数验证：不让 AI 算术

Agent B（评分员）会给每个选题打 6 个维度的分。但系统不信赖 AI 的算术能力——加权总分是用 Python 重新计算的。

Python # Agent B 给出 6 个维度的分数 scores = { "novelty": 8, "depth": 7, "relevance": 9, "actionability": 6, "trend": 8, "audience_fit": 7, } # 权重 weights = { "novelty": 0.25, "depth": 0.20, "relevance": 0.20, "actionability": 0.15, "trend": 0.10, "audience_fit": 0.10, } # 用 Python 重算，不信任 AI 的算术 total = sum(scores[k] * weights[k] for k in scores)
English
第 2-8 行：Agent B 给出 6 个维度的分数（新颖性、深度、相关性、可操作性、趋势、受众匹配度）
第 11-18 行：每个维度有不同的权重——新颖性最重要（25%），趋势和受众匹配度权重最低（各 10%）
第 21 行：用 Python 的 sum() 函数精确计算加权总分——不让 AI 做算术，因为 AI 经常算错
为什么重要：LLM 经常在算术上犯错（比如把 0.25+0.20 算成 0.46）。程序化计算确保分数永远准确
💡
AI 不擅长的事

LLM 擅长理解语言、创造内容，但不擅长精确计算。让 AI 做算术就像让诗人做会计——不是不能做，但你不会信任结果。这个设计原则是：让 AI 做它擅长的事（创造、评估），让代码做它擅长的事（精确计算、流程控制）。

反幻觉事实列表：让 AI 不乱编

幻觉是 AI 最大的问题之一——它会一本正经地编造不存在的事实。这个系统用"事实列表"来对抗幻觉。

📋
事实列表的工作原理

在正文生成之前，一个专门的"资料收集 Agent"会阅读所有原始文章，提取出结构化的事实列表（时间、地点、事件、人物、产品名等）。这个列表会被注入到后续所有 Agent 的提示词中——AI 被要求只使用列表中的事实，不能自己编造。

1
资料收集 Agent 阅读原始文章

提取所有可验证的事实：时间、地点、事件、人物、产品名称、数据

2
生成结构化事实列表

格式化为 JSON，每个事实标注来源（哪篇文章说的）

3
注入到所有后续 Agent 的 Prompt

每个 Agent 的提示词都包含这个事实列表，要求"只使用列表中的事实"

4
输出的文章有据可查

每个数据点都能追溯到原始来源，大大降低幻觉风险

截断 JSON 修复：AI 输出不完整时的救命稻草

AI 生成 JSON 时，有时会因为 max_tokens 限制被截断——输出到一半就停了。这个系统有一个聪明的修复机制。

Python def _repair_truncated_json(s: str): """尝试修复被 max_tokens 截断的 JSON。""" stack = [] # 追踪嵌套顺序 in_string = False escape_next = False for ch in s: if escape_next: escape_next = False continue if ch == "\\": escape_next = True continue if ch == '"' and not escape_next: in_string = not in_string
English
第 1 行：这个函数专门修复被截断的 JSON——AI 输出到一半被 max_tokens 卡住了
第 4 行：stack 是一个栈，记录遇到的 { 和 [ 的顺序——就像一摞盘子，后进先出
第 5-6 行：in_string 追踪当前是否在引号内，escape_next 追踪是否遇到了转义符 \
第 8-14 行：逐字符扫描——遇到 \ 就跳过下一个字符（转义），遇到 " 就切换 in_string 状态
原理：通过追踪括号嵌套，知道缺了几个 } 和 ]，然后补上，让 JSON 重新合法
🔧
为什么需要这个？

LLM 的输出长度受 max_tokens 限制。如果 JSON 太长，输出会被截断，导致不完整。比如 {"name": "张三", "age 就停了。修复机制会追踪括号嵌套，补上缺失的 : 25}，让 JSON 重新合法。

当事情出错时

AI 不是万能的——它会犯错、会幻觉、会格式错误。学会调试 AI 流水线，你就能摆脱 AI 的 bug 循环

AI 流水线的 5 种常见故障

🚫

JSON 解析失败

AI 输出的 JSON 格式不合法——多了逗号、少了引号、被截断。这是最常见的故障。

👻

幻觉输出

AI 编造不存在的数据——比如虚构一个产品名称或统计数据。发布出去就是假新闻。

⏰

超时

AI 响应太慢或完全无响应。可能是模型过载，也可能是提示词太长。

📝

输出质量差

AI 输出的内容不符合预期——可能是提示词不够清晰，也可能是模型能力不足。

💰

积分不足

用户的积分余额不够执行操作。系统返回 402 状态码，前端弹出充值窗口。

调试 AI 输出：当 AI 给了你一坨垃圾

当 AI 流水线返回错误结果时，你需要像侦探一样排查。以下是排查步骤：

1
检查原始 AI 输出

日志中找到 LLM 返回的原始文本。看看是格式问题还是内容问题。

2
检查 JSON 解析结果

parse_json_loose() 是否返回了 None？如果是，说明 AI 输出格式不对。

3
检查输入数据

传给 Agent 的数据是否正确？空数据或异常数据会导致 AI 输出异常。

4
检查提示词

提示词是否清晰？是否包含了所有必要信息？AI 的输出质量直接取决于提示词质量。

5
检查模型选择

是否用了合适的模型？简单任务用 DeepSeek，复杂创意任务用 Claude。

积分系统：402 响应的优雅处理

当用户积分不足时，系统返回 HTTP 402 状态码，前端自动弹出充值窗口。

JavaScript // 前端拦截 402 响应 api.interceptors.response.use( response => response, error => { if (error.response?.status === 402) { // 触发自定义事件，弹出充值窗口 window.dispatchEvent(new CustomEvent( 'show-credit-dialog', { detail: error.response.data } )); } return Promise.reject(error); } );
English
第 2 行：在 Axios（HTTP 客户端）上设置拦截器——所有响应都会先经过这里
第 5 行：检查状态码是否为 402（需要付费）
第 7-10 行：触发一个自定义事件 show-credit-dialog，把后端返回的积分信息传给弹窗组件
设计亮点：用 CustomEvent 解耦——API 层不需要知道弹窗组件的存在，只需要"喊一声"，弹窗组件自己会响应
