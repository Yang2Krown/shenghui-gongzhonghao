聪明的工程技巧

这个系统里有几个特别聪明的设计——理解它们，你就能在自己的项目中复制这些模式

"创造者而非过滤器"哲学

传统的信息处理思路是：爬 100 条 → 过滤到 10 条 → 输出。但这个系统反其道而行之：

🎯
核心洞察

Agent A（选题衍生员）不是从一堆烂选题里挑好的——它是主动创造好选题。给它 1 条资讯，它能衍生出 3-8 个高质量的候选选题。这就像一个创意总监，不是在废纸篓里找创意，而是从零开始构思。

❌

传统思路：过滤器

爬 100 条 → 用规则过滤掉 90 条 → 剩下 10 条 → 输出。问题是：如果原始数据质量不高，你过滤后也没好东西。

✅

这个系统：创造者

爬 1 条 → Agent A 衍生 5 个好选题 → Agent B 独立评分 → 输出最好的。原始数据质量低也没关系，Agent A 会创造价值。

程序化分数验证：不让 AI 算术

Agent B（评分员）会给每个选题打 6 个维度的分。但系统不信赖 AI 的算术能力——加权总分是用 Python 重新计算的。

Python # Agent B 给出 6 个维度的分数 scores = { "novelty": 8, "depth": 7, "relevance": 9, "actionability": 6, "trend": 8, "audience_fit": 7, } # 权重 weights = { "novelty": 0.25, "depth": 0.20, "relevance": 0.20, "actionability": 0.15, "trend": 0.10, "audience_fit": 0.10, } # 用 Python 重算，不信任 AI 的算术 total = sum(scores[k] * weights[k] for k in scores)
English
第 2-8 行：Agent B 给出 6 个维度的分数（新颖性、深度、相关性、可操作性、趋势、受众匹配度）
第 11-18 行：每个维度有不同的权重——新颖性最重要（25%），趋势和受众匹配度权重最低（各 10%）
第 21 行：用 Python 的 sum() 函数精确计算加权总分——不让 AI 做算术，因为 AI 经常算错
为什么重要：LLM 经常在算术上犯错（比如把 0.25+0.20 算成 0.46）。程序化计算确保分数永远准确
💡
AI 不擅长的事

LLM 擅长理解语言、创造内容，但不擅长精确计算。让 AI 做算术就像让诗人做会计——不是不能做，但你不会信任结果。这个设计原则是：让 AI 做它擅长的事（创造、评估），让代码做它擅长的事（精确计算、流程控制）。

反幻觉事实列表：让 AI 不乱编

幻觉是 AI 最大的问题之一——它会一本正经地编造不存在的事实。这个系统用"事实列表"来对抗幻觉。

📋
事实列表的工作原理

在正文生成之前，一个专门的"资料收集 Agent"会阅读所有原始文章，提取出结构化的事实列表（时间、地点、事件、人物、产品名等）。这个列表会被注入到后续所有 Agent 的提示词中——AI 被要求只使用列表中的事实，不能自己编造。

1
资料收集 Agent 阅读原始文章

提取所有可验证的事实：时间、地点、事件、人物、产品名称、数据

2
生成结构化事实列表

格式化为 JSON，每个事实标注来源（哪篇文章说的）

3
注入到所有后续 Agent 的 Prompt

每个 Agent 的提示词都包含这个事实列表，要求"只使用列表中的事实"

4
输出的文章有据可查

每个数据点都能追溯到原始来源，大大降低幻觉风险

截断 JSON 修复：AI 输出不完整时的救命稻草

AI 生成 JSON 时，有时会因为 max_tokens 限制被截断——输出到一半就停了。这个系统有一个聪明的修复机制。

Python def _repair_truncated_json(s: str): """尝试修复被 max_tokens 截断的 JSON。""" stack = [] # 追踪嵌套顺序 in_string = False escape_next = False for ch in s: if escape_next: escape_next = False continue if ch == "\\": escape_next = True continue if ch == '"' and not escape_next: in_string = not in_string
English
第 1 行：这个函数专门修复被截断的 JSON——AI 输出到一半被 max_tokens 卡住了
第 4 行：stack 是一个栈，记录遇到的 { 和 [ 的顺序——就像一摞盘子，后进先出
第 5-6 行：in_string 追踪当前是否在引号内，escape_next 追踪是否遇到了转义符 \
第 8-14 行：逐字符扫描——遇到 \ 就跳过下一个字符（转义），遇到 " 就切换 in_string 状态
原理：通过追踪括号嵌套，知道缺了几个 } 和 ]，然后补上，让 JSON 重新合法
🔧
为什么需要这个？

LLM 的输出长度受 max_tokens 限制。如果 JSON 太长，输出会被截断，导致不完整。比如 {"name": "张三", "age 就停了。修复机制会追踪括号嵌套，补上缺失的 : 25}，让 JSON 重新合法。

每个候选选题会被 4 个虚拟角色独立评分。如果评分差距很大，说明这个选题有争议——需要人工审查。

⚠️
分歧检测

如果 4 个角色的评分差距 ≥ 4 分（比如一个给 9 分，一个给 5 分），系统会标记这个选题为"有争议"——建议人工审查。这避免了 AI 过于自信地推荐一个实际上有风险的选题。
