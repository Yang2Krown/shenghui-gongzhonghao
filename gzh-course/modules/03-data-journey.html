三层过滤：省钱的艺术

嵌入（Embedding）是需要花钱的 API 调用。为了省钱，系统在嵌入之前设置了三层过滤：

1
时间过滤

超过 90 天的内容直接丢弃。过时的资讯没有价值。

2
AI 相关性过滤

用关键词判断内容是否和 AI 相关。不相关的直接跳过。

3
权重过滤

低权重来源（weight ≤ 2）的内容直接跳过。因为这些来源质量不高，不值得花钱做嵌入。

💡
这个设计很聪明

只有通过三层过滤的内容才会被送去嵌入。这就像一个漏斗——先用免费的规则筛掉大部分垃圾，再用花钱的 AI 处理精华内容。成本可能降低 60-70%。

语义聚类：让计算机"理解"文字

计算机不懂中文。但如果我们把一段文字变成一组数字（向量），计算机就能计算两段文字的"距离"——距离越近，意思越相似。

Python # 嵌入：把文字变成 1024 维的数字数组 embedding = await embed("GPT-5 发布了新功能") # 结果：[0.023, -0.156, 0.891, ...]（共 1024 个数字） # 语义聚类：和已有信息比对 for existing in existing_embeddings: distance = cosine_similarity(embedding, existing) if distance > 0.85: # 非常相似，归为同一组 merge_into_cluster(existing, new_info)
English
第 1-3 行：调用 DashScope 的嵌入 API，把"GPT-5 发布了新功能"变成 1024 个数字
第 5-9 行：遍历所有已有的信息向量，计算新信息和每个已有信息的"距离"
第 7-8 行：如果距离 > 0.85（非常相似），就把它们归为同一组（InfoCluster）
类比：就像图书馆把同一主题的书放在一起——系统把讨论同一话题的文章归为一组
📊
pgvector：向量数据库

这些向量存储在 pgvector 中。它能在百万级向量中快速找到最相似的几个——这比遍历所有向量快得多。阈值 0.85 意味着只有"非常相似"的内容才会被合并。

波次调度：避免把 API 打爆

系统每天要从 13 个信息源抓取数据。如果同时请求所有源，很容易被 API 限流甚至封禁。

🌊
波次调度（Wave Scheduling）

想象你在餐厅点菜。如果 100 个人同时点菜，厨房会崩溃。但如果分 5 波，每波 20 个人，每波之间等 2 分钟，厨房就能从容应对。系统的爬虫也是这样——每天 5 波（06:00、10:00、14:00、18:00、22:00），每波内的源按 90 秒间隔依次请求。

Python # 限流并发抓取（最多 5 个同时跑，避免 API 限流） sem = asyncio.Semaphore(5) task_sources = [] tasks = [] for src in sources: adapter = self.get_adapter(src.source_type) async def _limited_fetch(a=adapter, s=src): async with sem: return await self._fetch_one(a, s) tasks.append(_limited_fetch())
English
第 2 行：创建一个"信号量"（Semaphore），最多允许 5 个爬虫同时运行
第 4-5 行：遍历所有需要抓取的信息源
第 7-9 行：每个爬虫在执行前必须先获取"通行证"（async with sem）
类比：就像高速公路的收费站——最多 5 个车道同时通行，其他的排队等候

双重去重：同一条信息不会出现两次

不同信息源可能报道同一件事。系统用两种方式防止重复：

💾

内存去重

同一波次内，用内存中的 Set 记录已经处理过的标题哈希。新加入的记录在数据库中还不可见，所以需要内存去重。

🗄️

数据库去重

跨波次去重，查数据库中是否已有相同标题（哈希匹配）或完全相同的 URL。这是最终防线。

⚠️
为什么需要双重去重？

如果只用数据库去重，同一波次内新增的记录在数据库中还查不到（因为还没 commit），就会导致重复。内存去重解决了这个问题。
